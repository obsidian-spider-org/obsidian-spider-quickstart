# Cost-Aware Routing Swarm From One Copilot Request

I built a single markdown prompt that runs a cost-aware routing swarm: one parent call dispatches N independent subagents, each routed to the cheapest model that does the job, and a final synthesis pass gathers them. Every subagent's verdict is written to an HMAC-signed JSONL log you can audit later. The pattern works on GitHub Copilot Pro+ (current pricing window), on free vendor mesh (OpenRouter / Groq / Together / Cerebras with backoff/retry), on Claude Code's Agent tool, and on anywhere a parent agent can launch subagents.

If you don't already use an LLM agent harness, this won't matter to you today; it's a tool for people already paying for one. If you do, the bones of this are mostly free, because most coding-agent harnesses bill by the parent message, not by the fan-out inside it.

It's MIT-licensed. There's no service to sign up for. The whole thing is one prompt file plus two stdlib-only Python helpers. You can try it on a real input in about ten minutes.

This post walks through what it does, why I built it, the prompt itself, the audit-log format, and what to expect when you run it.

## Why I built it

I was reviewing pull requests with a single Copilot session and kept noticing one-shot misses. Things that a second pair of eyes would have caught in five seconds: an unparameterized SQL query, a swallowed exception, a naming-convention break that the linter doesn't enforce.

The obvious move is "run the diff through Copilot N times with different framing prompts." That works, but it costs N premium requests, and the outputs aren't linked to each other in any auditable way.

So I tried something simpler. I wrote a parent-prompt that tells the Copilot session itself to spawn N reviewer subagents inside the same message. Each subagent gets a different role (security, logic, style, performance, edge-cases, etc.) and emits one signed JSONL line. The parent collects them into a chain and writes a summary at the end.

The interesting bit is the billing. Copilot Pro+ counts the parent call as one premium request. The subagents spawned inside that parent message inherit the context and don't each bill separately, at least as of the current Copilot policy at time of writing. So one premium request gives you four to eight independent reviewers.

I default to a 2x4 formation (two waves of four reviewers). That's eight independent perspectives on a diff for the price of one premium request, plus a tamper-evident log of who said what.

## What you get after ten minutes

A JSONL audit trail like this:

```json
{"seq":1,"ts":"2026-05-13T12:00:01Z","prev_sha16":"0000000000000000","this_sha16":"a3f7c2d1e8b94f05","verb":"OBSERVE","agent":"reviewer-w1-a1","wave":1,"role":"security","task_id":"pr-42","claim":"SQL query on line 87 is unparameterized.","evidence":{"location":"src/db.py:87","detail":"f-string interpolation directly into cursor.execute(); exploitable via search input"},"severity":"high","confidence":"7/8","rh_flags":[]}
{"seq":2,"ts":"2026-05-13T12:00:02Z","prev_sha16":"a3f7c2d1e8b94f05","this_sha16":"b8e3a1c0f2d74e91","verb":"PASS","agent":"reviewer-w1-a2","wave":1,"role":"logic","task_id":"pr-42","claim":"no issues found in role scope","evidence":{},"severity":"info","confidence":"7/8","rh_flags":[]}
```

Each line is self-describing. `prev_sha16` chains to the previous receipt; `this_sha16` is the HMAC of the current one. You can re-verify the chain later with a stdlib-only Python script and detect any post-hoc edits.

You also get a reward-hack pattern detector, a small script that scans the chain for common LLM failure modes: copy-paste quorum (multiple agents claiming the same finding with identical evidence), citation-shape gaming (cosmetic `seq=1, sha16=0000...` that doesn't reference anything real), and confidence inflation (claims of `8/8` confidence without a human sign-off).

## The prompt, broken down

The parent-prompt has three configurable slots: `FORMATION`, `TARGET`, and `TIER_MIX`.

```
FORMATION=2x4          # X waves × Y subagents
TARGET=<paste PR diff or doc excerpt here>
TIER_MIX=all-frontier  # or: multi-tier
```

`FORMATION=X_Y` means X sequential waves of Y subagents each. Waves are sequential: wave 2 sees wave 1's JSONL output before it starts, so later waves can dispute or build on earlier findings rather than repeat them.

Here's the table of formations I use:

| Formation | Waves | Agents/wave | Total | When to use |
|-----------|-------|-------------|-------|-------------|
| `1x4`     | 1     | 4           | 4     | Single broad review pass |
| `2x4`     | 2     | 4           | 8     | Recommended start: first wave finds, second wave verifies |
| `4x8`     | 4     | 8           | 32    | Sustained adversarial review |
| `8x8`     | 8     | 8           | 64    | Heavy red-team; burns context fast |

I start every project at `2x4` and almost never climb above it. The `8x8` profile exists for stress-testing and high-stakes reviews; it burns context fast and the output gets noisy.

`TIER_MIX` is a knob for cost control. `all-frontier` runs every subagent at the same tier as the parent (default). `multi-tier` runs one anchor reviewer per wave at the frontier tier and the rest at a cheaper reasoning tier. Useful when you're metering tokens, not when you're metering premium requests.

## The HMAC chain

Each subagent emits one signed JSONL line. The chain rule:

- Wave 1, Agent 1: `prev_sha16 = "0000000000000000"`.
- Every subsequent receipt: `prev_sha16` equals the `this_sha16` of the immediately preceding receipt.
- `this_sha16 = HMAC-SHA256(key=HMAC_KEY, msg=f"{seq}|{ts}|{verb}|{claim}")[0:16]`.

The default key in the repo is `default-public-key-rotate-yours`. If you don't rotate, anyone reading the repo can forge a valid chain. Setting your own key takes thirty seconds: `export FANOUT_HMAC_KEY=<your-secret>`.

The HMAC layer is optional. If you don't care about tamper-evidence, ignore it; the prompt still produces structured JSONL output you can grep. If you do care, the chain costs nothing extra at runtime and gives you "who said what, and was it modified" semantics for free.

Verifying the chain after the fact is a one-liner:

```bash
python3 hmac_verifier.py runs/2026-05-13_pr-42/chain.jsonl
```

The script walks the chain, recomputes each HMAC, and exits non-zero if any link is broken. Stdlib only, no external dependencies.

## The reward-hack detector

LLMs do interesting things when you ask them for structured output and grade them by structure. They emit `seq=1, sha16=0000...` to satisfy the regex without referencing anything real. They emit the same finding eight times with cosmetically different wording to look like a quorum. They mark themselves `8/8 confidence` because the schema field accepts it.

The detector is a stdlib Python script that scans the chain for these patterns:

- **Copy-paste quorum**: two agents from the same wave with identical claims and identical evidence locations
- **Citation-shape gaming**: receipts whose `evidence.location` is empty, a placeholder, or doesn't appear in the TARGET text
- **Confidence inflation**: any receipt with `confidence: "8/8"` (the cap is 7/8; eighth point requires human sign-off)
- **HMAC break**: any `prev_sha16` that doesn't match the previous `this_sha16`

It's not exhaustive. It catches the obvious failure modes I've hit repeatedly. I add new patterns as I find them.

```bash
python3 reward_hack_detector.py runs/2026-05-13_pr-42/chain.jsonl
```

The output is a small JSON report with one entry per flag. If the chain is clean, the report is empty.

## What it doesn't do

Honest list:

- **It is not a substitute for a broken pipeline.** If your tests don't run, no number of reviewer agents will catch a runtime regression. Use this to augment review, not replace CI.
- **Inside-parent-message subagent counting is current Copilot pricing-window behavior, not a contractual guarantee.** GitHub announced [usage-based billing effective June 1, 2026](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/); the cost model in this post reflects pre-transition behavior. Measure your own.
- **Confidence is capped at 7/8.** The eighth point requires a human quorum certificate. The prompt is hard-coded to refuse `8/8` self-claims. Don't ship AI-only-reviewed code to production and call it "fully reviewed."
- **Context exhaustion is real.** A `4x8` run on a large diff can exhaust the parent context window before wave 4 finishes. Start with `2x4` and measure.
- **It doesn't include the orchestrator I run internally.** The bigger pipeline (BFT quorum across multiple model families, cross-substrate identity rehydration, vendor-mesh telemetry) is internal scaffolding that isn't packaged for outside use. The markdown prompt is the standalone slice.

## Tiers and formations, a worked example

Suppose you have a small PR, a 100-line bugfix in a Python service. What I'd do:

1. `cp .env.example .env`, set `HMAC_KEY` to a random 32-char string.
2. Open Copilot Pro+ coding-agent surface on the PR.
3. Paste `PROMPT.md`. Set `FORMATION=2x4`, paste the diff into `TARGET`, leave `TIER_MIX=all-frontier`.
4. Send. Wait for the JSONL output.

What I expect: eight subagents fire across two waves. Five to seven of them emit `OBSERVE` receipts (real findings). One or two emit `PASS` (nothing in their role scope). The parent emits one `SUMMARIZE` receipt at the end listing the unique finding IDs and any consensus flags.

The interesting failure mode I see most often is the model collapsing to one answer: the parent sometimes assigns all subagents the same implicit framing and produces a quorum of identical findings with cosmetically different wording. The reward-hack detector catches the obvious form. The subtle form (alignment collapse where all agents converge on the same blind spot) is harder. The cure is to mandate different roles per agent and to read the receipts critically, not just count them.

For a larger PR, say a 500-line refactor, I'd jump to `4x8` and pre-summarize the diff first (don't paste the full diff into TARGET; paste a section plus the relevant context). Wave 4 in a `4x8` run often disputes findings from waves 1-3, which is exactly the structured disagreement I'm paying premium-request budget for.

## Cost model: measure your own

[Copilot Pro+](https://github.com/features/copilot/plans) is $39/month with 1500 premium requests; overage is $0.04/request. Each parent call costs one premium request. Subagents spawned inside that parent message inherit context and don't each bill separately under the current Copilot pricing window.

[Model multipliers per the Copilot docs](https://docs.github.com/en/copilot/concepts/billing/copilot-requests): GPT-5.5 at 7.5×, Claude Opus 4.7 at 15×, Sonnet 4.6 at 1×. One parent call on GPT-5.5 = 7.5 premium requests ≈ $0.30 of overage budget.

GitHub announced [usage-based Copilot billing effective June 1, 2026](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/); the current Copilot subagent pricing window is closing, so measure your own savings before then. The routing pattern keeps working afterward; only the Copilot-specific multiplier compresses.

### Measure your own cost savings

Don't trust my number; calculate yours. The headline ratio is 100×–1000× depending on which frontier model you'd otherwise pay for. Plug your numbers in:

```
INPUT_TOKENS_PER_SUBAGENT   = 200,000   (max prompt + context rehydration)
OUTPUT_TOKENS_PER_SUBAGENT  = 50,000
SUBAGENTS_PER_PARENT        = 40
TOOL_CALLS_PER_SUBAGENT     = 25        (midpoint of 10-40)
TOKENS_PER_TOOL_CALL_LOOP   = 5,000     (input re-context per tool round-trip)
INPUT_PRICE_PER_MTOK_USD    = 5.00      (Claude Opus 4.7 or GPT-5.5; check your model)
OUTPUT_PRICE_PER_MTOK_USD   = 25.00     (Opus 4.7; 30.00 for GPT-5.5)
YOUR_PARENT_CALL_COST_USD   = 0.30      (Copilot Pro+ GPT-5.5 overage rate)

total_input_tokens =
    INPUT_TOKENS_PER_SUBAGENT * SUBAGENTS_PER_PARENT
  + TOKENS_PER_TOOL_CALL_LOOP * TOOL_CALLS_PER_SUBAGENT * SUBAGENTS_PER_PARENT
  + 200_000

total_output_tokens =
    OUTPUT_TOKENS_PER_SUBAGENT * SUBAGENTS_PER_PARENT
  + 50_000

raw_api_cost_usd =
    (total_input_tokens  / 1_000_000) * INPUT_PRICE_PER_MTOK_USD
  + (total_output_tokens / 1_000_000) * OUTPUT_PRICE_PER_MTOK_USD

savings_multiplier = raw_api_cost_usd / YOUR_PARENT_CALL_COST_USD
```

My normal workflow on Copilot Pro+ (40 subagents on GPT-5.5): total_input ≈ 13.2M, total_output ≈ 2.05M, raw_api_cost ≈ $127.50, savings_multiplier = $127.50 / $0.30 ≈ **425×**. Heavy Opus 11x8 max-burn priced against Opus raw lands near 961×. Pessimistic floor (cheapest current frontier across the board) lands near 123×. The 100×–1000× range is honest at both ends.

## What's next

The minimal slice is what's in the repo. If you outgrow JSONL (say, you want bitemporal audit, queryable history, or rollback), the upgrade path is Postgres with an append-only receipts table plus an XTDB-style bitemporal layer. There's a doc in the repo (`UPGRADE_TO_POSTGRES.md`) with the schema and migration path.

That bigger infrastructure is what I actually run for my own work. The markdown prompt above is the minimal public slice. The upgrade is optional; most projects never need it.

If you want the architecture context, `BOOTSTRAP_NOTE.md` in the repo describes how the prompt was developed (cross-substrate authoring, multi-agent review of the prompt itself, structured disagreement gates). It's interesting context but not required reading.
