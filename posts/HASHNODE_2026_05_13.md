# Cost-Aware Routing Swarm From One Copilot Request

I'm an indie dev who self-hosts most of my tooling, and I built a single markdown prompt that runs a cost-aware routing swarm: one parent call dispatches N independent subagents inside the same message, each routed to the cheapest model that does the job, and a final synthesis pass gathers them. Each subagent's verdict is written to an HMAC-signed JSONL log I can audit later. The pattern works on GitHub Copilot Pro+ (current pricing window), on free vendor mesh (OpenRouter / Groq / Together / Cerebras with backoff/retry), on Claude Code's Agent tool, and on anywhere a parent agent can launch subagents.

If you don't already use an LLM agent harness, this won't matter to you today; it's a tool for people already paying for one. If you do, the bones of this are mostly free, because most coding-agent harnesses bill by the parent message, not by the fan-out inside it.

It's MIT-licensed. Everything runs locally. No service to sign up for, no telemetry, no license keys. The whole thing is one prompt file plus two stdlib-only Python helpers. If you've ever been frustrated that "code review assistants" all want to be a SaaS, this is the opposite of that: it's a text file you paste into the model surface you already pay for.

This post walks through what it does, why I built it, the prompt itself, the audit-log format, and what to expect when you run it on your own pipeline.

## Why I built it

I was reviewing pull requests with a single Copilot session and kept noticing one-shot misses: an unparameterized SQL query, a swallowed exception, a naming-convention break the linter doesn't enforce. The obvious move is "run the diff through Copilot N times with different framing prompts," but that costs N premium requests and the outputs aren't linked to each other in any auditable way.

So I tried something simpler. I wrote a parent-prompt that tells the Copilot session itself to spawn N reviewer subagents inside the same message. Each subagent gets a different role (security, logic, style, performance, edge-cases, etc.) and emits one signed JSONL line. The parent collects them into a chain and writes a summary at the end.

The interesting bit for self-hosters: Copilot Pro+ counts the parent call as one premium request. The subagents spawned inside that parent message inherit the context and don't each bill separately, at least as of the current Copilot policy. So one premium request gives you four to eight independent reviewers, and the audit log lives on your own filesystem with no external dependencies.

I default to a 2x4 formation (two waves of four reviewers). That's eight independent perspectives on a diff for the price of one premium request, plus a tamper-evident log of who said what.

## What you get after ten minutes

A JSONL audit trail like this:

```json
{"seq":1,"ts":"2026-05-13T12:00:01Z","prev_sha16":"0000000000000000","this_sha16":"a3f7c2d1e8b94f05","verb":"OBSERVE","agent":"reviewer-w1-a1","wave":1,"role":"security","task_id":"pr-42","claim":"SQL query on line 87 is unparameterized.","evidence":{"location":"src/db.py:87","detail":"f-string interpolation directly into cursor.execute(); exploitable via search input"},"severity":"high","confidence":"7/8","rh_flags":[]}
{"seq":2,"ts":"2026-05-13T12:00:02Z","prev_sha16":"a3f7c2d1e8b94f05","this_sha16":"b8e3a1c0f2d74e91","verb":"PASS","agent":"reviewer-w1-a2","wave":1,"role":"logic","task_id":"pr-42","claim":"no issues found in role scope","evidence":{},"severity":"info","confidence":"7/8","rh_flags":[]}
```

Each line is self-describing. `prev_sha16` chains to the previous receipt; `this_sha16` is the HMAC of the current one. You re-verify the chain later with a stdlib-only Python script. No external dependencies, no daemon, no service.

You also get a reward-hack pattern detector, a small script that scans the chain for common LLM failure modes: copy-paste quorum, citation-shape gaming, confidence inflation. Stdlib only.

## The prompt, broken down

The parent-prompt has three configurable slots:

```
FORMATION=2x4          # X waves × Y subagents
TARGET=<paste PR diff or doc excerpt here>
TIER_MIX=all-frontier  # or: multi-tier
```

`FORMATION=X_Y` means X sequential waves of Y subagents each. Waves are sequential: wave 2 sees wave 1's JSONL output before it starts, so later waves can dispute or build on earlier findings rather than repeat them.

| Formation | Waves | Agents/wave | Total | When to use |
|-----------|-------|-------------|-------|-------------|
| `1x4`     | 1     | 4           | 4     | Single broad review pass |
| `2x4`     | 2     | 4           | 8     | Recommended start: first wave finds, second wave verifies |
| `4x8`     | 4     | 8           | 32    | Sustained adversarial review |
| `8x8`     | 8     | 8           | 64    | Heavy red-team; burns context fast |

I start every project at `2x4` and almost never climb above it.

`TIER_MIX` is a cost knob. `all-frontier` runs every subagent at the parent's tier (default). `multi-tier` runs one anchor reviewer per wave at the frontier tier and the rest at a cheaper reasoning tier.

## The HMAC chain

Each subagent emits one signed JSONL line. The chain rule:

- Wave 1, Agent 1: `prev_sha16 = "0000000000000000"`.
- Every subsequent receipt: `prev_sha16` equals the `this_sha16` of the immediately preceding receipt.
- `this_sha16 = HMAC-SHA256(key=HMAC_KEY, msg=f"{seq}|{ts}|{verb}|{claim}")[0:16]`.

The default key in the repo is `default-public-key-rotate-yours`. Rotate it (`export FANOUT_HMAC_KEY=<your-secret>`) and now anyone who hasn't seen your key can't forge a valid chain on your logs.

Verify the chain after the fact with one command:

```bash
python3 hmac_verifier.py runs/2026-05-13_pr-42/chain.jsonl
```

The script walks the chain, recomputes each HMAC, and exits non-zero if any link is broken. Stdlib only. You can put this in your CI.

## The reward-hack detector

LLMs find creative ways to satisfy a schema without doing the underlying work. They emit `seq=1, sha16=0000...` placeholders that pass the regex. They emit the same finding eight times with cosmetically different wording to look like a quorum. They mark themselves `8/8 confidence` because the schema accepts it.

The detector scans the chain for:

- **Copy-paste quorum**: two agents from the same wave with identical claims and identical evidence locations
- **Citation-shape gaming**: receipts whose `evidence.location` is empty, a placeholder, or doesn't appear in TARGET
- **Confidence inflation**: any receipt with `confidence: "8/8"` (the cap is 7/8; eighth point requires human sign-off)
- **HMAC break**: any `prev_sha16` that doesn't match the previous `this_sha16`

```bash
python3 reward_hack_detector.py runs/2026-05-13_pr-42/chain.jsonl
```

It's not exhaustive. It catches the obvious failure modes I've hit repeatedly. I add new patterns as I find them in my own runs.

## What it doesn't do

- **It is not a substitute for a broken pipeline.** If your tests don't run, reviewer agents won't catch a runtime regression. Augment review; don't replace CI.
- **Inside-parent-message subagent counting is current Copilot pricing-window behavior, not a contractual guarantee.** GitHub announced [usage-based billing effective June 1, 2026](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/); the cost model assumes pre-transition behavior. Measure your own.
- **Confidence caps at 7/8.** The prompt refuses `8/8` self-claims. Don't ship AI-only-reviewed code to production and call it "fully reviewed."
- **Context exhaustion is real.** A `4x8` run on a large diff can exhaust the parent context window before wave 4 finishes. Start small.
- **The internal pipeline I run is not in this repo.** What's here is the minimal public slice. The bigger system stays internal.

## Cost model: measure your own

[Copilot Pro+](https://github.com/features/copilot/plans) is $39/month, 1500 premium requests, $0.04/request overage. Each parent call costs one premium request; subagents inside that message inherit context and don't each bill separately under the current pricing window. [Multipliers per the Copilot docs](https://docs.github.com/en/copilot/concepts/billing/copilot-requests): GPT-5.5 = 7.5×, Opus 4.7 = 15×, Sonnet 4.6 = 1×.

GitHub announced [usage-based Copilot billing effective June 1, 2026](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/); the current Copilot subagent pricing window is closing, so measure your own savings before then. The routing pattern keeps working afterward; only the Copilot-specific multiplier compresses.

### Measure your own

Don't trust my number; plug yours in. The headline range is 100×–1000× depending on which frontier model you'd otherwise pay for:

```
raw_api_cost_usd =
    (total_input_tokens / 1_000_000) * INPUT_PRICE_PER_MTOK_USD
  + (total_output_tokens / 1_000_000) * OUTPUT_PRICE_PER_MTOK_USD

total_input_tokens =
    INPUT_TOKENS_PER_SUBAGENT * SUBAGENTS_PER_PARENT
  + TOKENS_PER_TOOL_CALL_LOOP * TOOL_CALLS_PER_SUBAGENT * SUBAGENTS_PER_PARENT
  + parent_input

savings_multiplier = raw_api_cost_usd / YOUR_PARENT_CALL_COST_USD
```

My normal workflow (40 subagents on GPT-5.5 via Copilot Pro+) measures around 425×; heavy Opus 11x8 max-burn priced against Opus raw lands near 961×; pessimistic floor (cheapest frontier across the board) lands near 123×.

## Upgrade path (if you outgrow JSONL)

If you want bitemporal audit, queryable history, or rollback semantics on the chain, the upgrade is Postgres with an append-only receipts table plus an XTDB-style bitemporal layer. There's a doc in the repo (`UPGRADE_TO_POSTGRES.md`) with the schema and migration path. Most projects never need it. Mine does because I run hundreds of agents.
